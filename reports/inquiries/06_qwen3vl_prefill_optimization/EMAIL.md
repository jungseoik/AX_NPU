안녕하세요~ PIA-SPACE 정서익입니다.

다름이 아니라, 현재 **Qwen3-VL-2B 를 최적화하는 작업**이 필요해서 연락드립니다.
AX 미니트랙 서현석 매니저님과 황지욱 엔지니어님께 **신규 릴리즈 버전이 있다**는 이야기를 들었습니다.

저희 목표는 **Qwen3-VL-2B 를 20채널 규모에서 1000ms 안쪽으로 처리**하는 것입니다.

- **현재 가용 가능한 NPU 는 2장** 입니다.
- **20채널** = 720p 이미지 20장이 **동시요청 또는 배치**로 들어올 때 전부 처리되는 시간입니다.
- 저희는 **TTFT(prefill 이후 첫 토큰까지의 시간)** 가 중요합니다.
  과업 특성상 **분류를 위해 토큰 1개만** 보기 때문입니다.

## 1. 현재 저희 측정 결과

먼저 저희가 어디까지 확인했는지 공유드립니다. 아래는 모두 **실측값**입니다.

### 측정 환경

| 항목 | 값 |
| --- | --- |
| 모델 | `mobilint/Qwen3-VL-2B-Instruct` (HF 커밋 `7202ab5b`, 2026-06-29 — 현재 최신) |
| NPU | ARIES, 드라이버 **1.13** / 펌웨어 1.2.5 |
| 런타임 | qbruntime **1.2.0** (SDK 번들 1.0v) |
| 라이브러리 | `mblt-model-zoo` **2.4.2**, `transformers` 4.57.1 |
| **코어모드** | vision / text 모두 **`global8`** (config.json 기본값, `target_clusters=[0,1]`) |
| 지표 | `max_new_tokens=1` 생성 시간 = **TTFT**, median (워밍업 1회 제외) |
| 측정 조건 | **유휴 카드에서 측정** — 측정 대상 NPU 는 다른 작업 없이 이 테스트만 수행 |
| 부하 분산 | 배치 미사용. **카드당 스레드 2개**로 동시 제출, 카드에 라운드로빈 |

### 단건 TTFT

| 해상도 | 전처리(CPU) | TTFT | TTFT 최저 |
| --- | ---: | ---: | ---: |
| 720p | 24.4 ms | 166.0 ms | **162.2 ms** |
| 1080p | 33.1 ms | 176.4 ms | **161.3 ms** |

두 해상도의 NPU 처리 시간이 동일했는데, 확인해보니 프로세서가 static 모드
(`dynamic_vision=False`)로 동작하면서 **입력을 224×224 로 고정 리사이즈**하고 있었습니다
(`_resize_one(img, size=(224, 224))`). 그 결과 어떤 해상도를 넣어도 동일한 그리드가 됩니다.

**원본 Qwen3-VL 프로세서와 비교하면 차이가 큽니다.** 동일 이미지, 동일 `patch_size=16`/`merge_size=2`:

| 입력 | 프로세서 | `image_grid_thw` | 패치 수 | **시각 토큰** |
| --- | --- | --- | ---: | ---: |
| 720p (1280×720) | `Qwen/Qwen3-VL-2B-Instruct` | `[1, 44, 80]` | 3520 | **880** |
| 720p (1280×720) | `mobilint/Qwen3-VL-2B-Instruct` | `[1, 16, 16]` | 256 | **64** |
| 1080p (1920×1080) | `Qwen/Qwen3-VL-2B-Instruct` | `[1, 68, 120]` | 8160 | **2040** |
| 1080p (1920×1080) | `mobilint/Qwen3-VL-2B-Instruct` | `[1, 16, 16]` | 256 | **64** |

원본은 해상도에 비례해 시각 토큰이 늘어나는데(720p 880개 / 1080p 2040개), NPU 빌드는
**해상도와 무관하게 64개**입니다. 720p 기준 **약 14배**, 1080p 기준 **약 32배** 적습니다.
`size` / `min_pixels` / `max_pixels` 를 지정해 보려 했으나, static 모드에서는 해당 오버라이드가
명시적으로 거부되도록 되어 있었습니다(고정 그리드로 컴파일된 MXQ 와 맞지 않기 때문으로 이해했습니다).

**이 부분이 저희에게는 속도보다 우선하는 문제입니다.**

저희가 Qwen3-VL 을 선택한 이유 자체가 **네이티브 해상도(native resolution) 처리 능력**을
활용하기 위해서입니다. 그런데 현재 NPU 빌드는 입력을 224×224 로 축소하므로,
**모델이 원래 가진 이해 능력을 오히려 깎는 결과**가 됩니다.
저희 과업은 CCTV 영상 기반 분류인데, 224×224 로 축소되면 **원거리 객체나 세부 단서가 사라집니다.**

**한 가지 말씀드릴 점은, 저희가 아래에 정리한 지연시간 수치가 정작 저희가 원하는 조건과는
거리가 있다는 것입니다.** 저희는 이 구성이 Qwen3-VL 의 네이티브 해상도를 살리는 방식이라고
이해하고 측정을 진행했는데, 확인해보니 실제로는 224×224 로 축소된 조건이었습니다.

따라서 아래 수치는 **저희가 실제로 필요로 하는 워크로드가 아닌, 정확도를 최대한 희생한
조건에서 나온 값**으로 봐주시면 됩니다. 그 상태에서도 목표에 미치지 못하고 있고,
네이티브 해상도를 지원하게 되면 TTFT 는 더 늘어날 것으로 예상합니다.

### 고해상도 MXQ 컴파일 관련 확인 요청

공개해 주신 튜토리얼(`compilation/vlm/`)을 살펴보니 아래와 같았습니다.

- `mblt_compile_vision.py` 에는 `--image-size` 인자가 있으나 **기본값이 `[224, 224]`** 입니다.
- 반면 `mblt_compile_language.py` 는 `image_size=(224, 224)` 가 **코드에 고정**되어 있고,
  README 에도 *"image size fixed at 224x224"* 로 명시되어 있습니다.
- 캘리브레이션 이미지 생성(`download_images.py`)도 224×224 로 고정되어 있습니다.
- `mblt-model-zoo` 에는 `_NPU_MAX_VISION_TOKENS = 2048` 이라는 상한이 정의되어 있어,
  시각 토큰이 최대 2048개까지는 가능한 것으로 보입니다(1080p 원본 기준 2040개와 유사한 수준).

여쭙고 싶은 것은 다음과 같습니다.

1. **고해상도로 MXQ 를 컴파일하면 이 문제가 해결되는지**, 그리고 **현재 지원되는지** 입니다.
   vision 만 `--image-size` 를 올려서는 안 되고 language 모델과 캘리브레이션까지 함께 맞춰야 할 것으로
   보이는데, 튜토리얼 상으로는 224×224 고정이 전제인 것으로 읽힙니다.
2. 지원된다면 **권장 절차와 상한**(시각 토큰 2048 기준 어느 해상도까지 가능한지)
3. 지원되지 않는다면, **고해상도 대응 빌드의 제공 계획**이 있는지

### 채널 수 × 카드 수 (720p, 실측)

| 채널 | NPU 1장 | NPU 2장 | 카드 확장 효율 |
| ---: | ---: | ---: | ---: |
| 16 | 2421.5 ms | 1270.2 ms | 1.91× |
| **20** | 3026.2 ms | **1579.8 ms** | 1.92× |
| 24 | 3596.8 ms | 1869.8 ms | 1.92× |

- 장당 처리시간이 1장 기준 **151.3 ms**, 2장 기준 **79.0 ms** 로 채널 수에 **선형**입니다.
- 카드 확장 효율은 1.91~1.92× 로 거의 손실이 없습니다.
- 카드 1장 안에서는 **스레드 2개에서 포화**했습니다(1스레드 3403ms → 2스레드 2415ms, 4·8스레드도 동일).

### 목표까지 남은 거리

| | 20채널 처리 시간 |
| --- | ---: |
| NPU 1장 | 3026 ms |
| **NPU 2장 (현재 가용 수량)** | **1580 ms** |
| **목표** | **1000 ms** |

**현재 구성으로는 목표 대비 약 1.58배 초과**입니다.

다만 앞서 말씀드린 대로 이 수치는 **224×224 축소 조건**에서 나온 것이라,
저희가 실제로 필요로 하는 네이티브 해상도 기준으로는 격차가 더 클 것으로 보입니다.
그래서 **속도(§①-1,2)와 해상도(§①-3) 두 가지를 함께 확인**드리고자 합니다.

### 배치 추론 시도 결과

배치로 처리하면 개선될 것으로 보고 시도했으나 아래 메시지로 진행하지 못했습니다.

```
ValueError: Batched Qwen3-VL text inference requires a 3-input
            [inputs, rope, deepstack] MXQ (the current Batch16 build).
            The legacy 2-input build ...
```

확인해보니 저희가 받은 text MXQ 는 입력이 2개(`inputs_embeds/reshape`, `deepstack_visual_embeds_0`)인
legacy 빌드였습니다. 또한 text MXQ 에는 Multi 번들이 없어(`Single`/`Global4`/`Global8` 만 존재)
`core_mode="multi"` 지정 시 `Model_MXQAndModelConfigNotMatch` 가 발생했습니다.
(vision MXQ 에는 Multi 번들이 있습니다)

공개해 주신 **SDK 튜토리얼(`compilation/vlm/`)의 language 컴파일은 RoPE 를 사전 계산해 모델에 굽는
방식**("Pre-cached RoPE embeddings")이라, 저희가 직접 컴파일해도 2입력 빌드만 만들어지는 것으로
이해했습니다. 배치는 행마다 위치가 달라 RoPE 가 런타임 입력이어야 하므로 3입력 빌드가
필요한 것으로 보입니다.

`mblt-model-zoo` 2.4.2 라이브러리 쪽은 배치 경로가 이미 준비되어 있는 것으로 보입니다.

## 2. 문의드리는 사항

### ① 신규 릴리즈 SDK 및 튜토리얼 문서

**신규 릴리즈에서 prefill 단계가 더 최적화되었다**고 들었습니다.
혹시 **해당 SDK 와 사용방법 튜토리얼 문서를 제공받을 수 있을지** 문의드립니다.

함께 확인하고 싶은 점은 아래와 같습니다.

1. 신규 릴리즈에 **3-input Batch16 text MXQ** 가 포함되는지, 포함된다면 배포 일정
2. 신규 릴리즈 적용 시 **20채널 / 1000ms** 목표에 도달 가능한 수준인지
   (현재 가용 수량인 2장 기준 1580ms 이므로 약 1.6배 개선이 필요합니다).
   목표 달성에 **필요한 NPU 수량**을 함께 알려주시면 자원 확보를 검토하겠습니다.
3. **고해상도(네이티브 해상도) 대응 빌드** 관련 — 위 §1 의 확인 요청 참조.
   토큰 수 대비 **TTFT 증가 폭**도 함께 알려주시면 속도·정확도 균형점을 잡는 데 도움이 되겠습니다.
4. vision/text **코어모드 권장 조합** — 현재 저희는 양쪽 `global8` 기본값을 쓰고 있는데,
   vision 을 `multi` 또는 `global4` 로 분리하는 편이 유리한지
5. 카드 1장을 코어 단위로 분할해(예: vision `global4`/cluster0, text `single`/core 1:0)
   **인스턴스를 여러 개 띄우는 방식**이 권장되는지

### ② 실증 기간 중 상위 NPU 교체 테스트 가능 여부

AX 미니트랙 실증 기간은 **1~2개월** 정도로 예상하고 있습니다.

- **10월 15일 설치**, 이후 **약 30일 운영** (그 이전 테스트 기간 포함)

이 실증 기간 동안 **좀 더 성능이 좋은 NPU 를 잠시 교체하여 테스트가 가능할지** 문의드립니다.
위 측정처럼 현재 구성으로는 목표에 미치지 못해, 결국 안정적인 서비스 검증 및 배포 실증을
위해서는 해당 작업이 필요할 것으로 보입니다.
