## 1. 회신 요지

### 1-1. 고해상도 — **신규 SDK에서 dynamic RoPE 지원 예정** ★

- **현재 공개 SDK 는 dynamic RoPE 를 지원하지 않아 이미지 사이즈가 고정되어야 한다.**
  → 우리가 조사한 "224×224 고정, 자체 컴파일로도 해제 불가"가 사실로 확인됐다.
- **`_NPU_MAX_VISION_TOKENS = 2048` 은 임의 제한이다.**
  실제 제약은 `vision token + prompt token < 컴파일 시 지정한 token sequence length 및 cache length`.
  **기본 4096**, single inference 모델은 **16K 까지도 지원**된다.
- **이번 주 또는 다음 주 공개될 신규 SDK 에서 dynamic RoPE 를 지원**한다.
  → 이미지 사이즈 고정이 불필요해진다.

### 1-2. 신규 릴리즈 성능 — 목표 달성에 부정적 ★

- 신규 릴리즈에서 확인한 속도: **16 batch 기준 약 5300 TPS**, 8 batch 에서도 **약 5000 TPS** 예상.
- 스트림당 환산: **5000 / 8 ≈ 625 TPS**.
- > "고화질 이미지(2000 토큰 이상 필요)에서 원하시는 TTFT 를 맞추기는 힘들어 보입니다."

### 1-3. 코어모드 권장

| 파트 | 권장 |
| --- | --- |
| **Vision 인코더** | single inference 면 **`global8` 이 가장 빠름**. 다만 **이미 카드 1장에서 batch 처리 중이라면 `single` 코어 8개 비동기가 가장 유리**할 수 있다. 추후 batch inference 에서도 vision 은 single 코어 비동기가 가장 빠를 것으로 봄 |
| **Text 디코더 (prefill)** | **`global8` 권장**. 비동기가 빠른 케이스는 `single` 코어. **추후 batch inference 에서는 Mobilint 가 내부적으로 코어를 관리**하므로 신경 쓰지 않아도 됨 |
| 공통 | 케이스마다 다르므로 **tracing 으로 직접 튜닝 권장** — `docs/advanced_usage.md`(qb Runtime Library 고급 기능)의 tracing 으로 NPU 사용량을 극대화하는 방향 |

### 1-4. 상위 NPU = MLA400

- 상위 NPU 는 **MLA400** 을 가리키며, **MLA100 4장을 쓰는 것과 같다.**
- > "일반적으로 latency 를 줄이기보단 **throughput 을 늘리는 데 유리**하다고 이해해주시는 것이 맞습니다."
- 실증 기간 교체 가능 여부는 **담당자에게 별도 문의 예정**.

## 2. 우리 조사와의 대조

| 우리가 확인했던 것 | 회신 |
| --- | --- |
| static 빌드가 224×224 고정, `size`/`min_pixels` 오버라이드 거부 | ✅ 사실 — dynamic RoPE 미지원이 원인 |
| 튜토리얼 두 브랜치 모두 224 고정, `--image-size` 가 최신 브랜치에서 사라짐 | ✅ 자체 컴파일로 해제 불가가 맞음 |
| `_NPU_MAX_VISION_TOKENS = 2048` 이 상한인 줄 알았음 | ❌ **임의 제한**. 실제는 seq/cache length(기본 4096, 최대 16K) |
| 2B 는 RoPE 가 구워진 2입력 빌드, 8B-Batch16 은 3입력 | 직접 언급 없음 — dynamic RoPE 지원으로 해소될 전망 |

## 3. 미답변 · 후속 확인 필요 ★

| # | 질의 | 상태 |
| --- | --- | --- |
| ①-1 | **2B 용 배치 대응 빌드 제공 여부·일정** | ❌ 명시적 답 없음 (신규 릴리즈 언급만) |
| ①-2 | 20채널 1000ms 도달 가능 여부 / **필요 NPU 수량** | △ 고해상도에선 어렵다는 취지, **수량은 미제시** |
| ①-3 | 토큰 수 대비 **TTFT 증가 폭·벤치마크** | ❌ 미제공 (TPS 수치만) |
| ② | 실증기간 MLA400 교체 | △ 담당자 문의 중 |

### ★ 가장 먼저 물어야 할 것 — TPS 기준

**"16 batch 5300 TPS" 가 카드 1장 기준인지 전체 기준인지가 명시되지 않았다.**
이 값에 따라 우리가 쓸 수 있는 해상도 예산이 2배 달라진다.

20채널 / 1000ms 조건에서 이미지당 허용 토큰 수를 역산하면:

| TPS 기준 | 2장 합산 처리량 | 이미지당 허용 토큰 | 대략 해상도 |
| --- | ---: | ---: | --- |
| 카드당 5000 TPS | 10,000 TPS | **≈ 500 토큰** | 패치 40×50 ≈ 640×800 |
| 전체 5000 TPS | 5,000 TPS | **≈ 250 토큰** | 패치 ~31×32 ≈ 500×512 |

(현재 224×224 = **64 토큰**, 720p 네이티브 = **880 토큰**)

즉 **어느 쪽이든 224×224 보다는 크게 개선되지만 720p 네이티브(880 토큰)에는 못 미친다.**
정확한 균형점을 잡으려면 TPS 기준을 먼저 확인해야 한다.

## 4. 우리 쪽 후속 작업

1. **신규 SDK 공개 시 즉시 확보** — dynamic RoPE 지원분. 이번 주~다음 주 예정
2. **TPS 기준 재문의** (카드당/전체) + 토큰 수별 TTFT 벤치마크 재요청
3. **코어모드 재실측** — 회신의 권장(vision: batch 시 `single` 8코어 비동기 / text prefill: `global8`)을
   우리 20채널 시나리오에서 검증. 현재 우리는 양쪽 `global8` + 카드당 2스레드
4. **tracing 튜닝** — `docs/advanced_usage.md` 의 tracing 으로 NPU 사용률 확인
5. **MLA400** — throughput 지향이라는 점을 감안해 우리 요구(TTFT)와 맞는지 재검토.
   20채널 동시요청은 throughput 성격이 강해 이득이 있을 수 있다

> 상황에 따라 single core로 비동기로 8개 코어를 각각 따로 사용하는 것이 유리한 경우도 있습니다. 예를 들어
> 어제 말씀 주신 것처럼 이미 MLA100 한 장에서 batch 처리 하고 있는 경우에는 single core로 비동기로
> 처리하는 것이 가장 유리할 수 있고, 추후 지원될 batch inference 상황에서도 vision encoder를 single core를
> 활용하여 비동기 처리하는 것이 가장 빠를 것으로 생각됩니다.
>
> Text decoder 파트는 prefill의 경우 역시 global8 코어를 권장 드리며, 비동기로 처리하는 것이 빠른
> 케이스에서는 single core를 권유드립니다. 추후 지원될 batch inference 상황에서는 저희가 내부적으로 코어
> 관리를 거의 하도록 되어 있어 이 부분은 신경 쓰지 않으셔도 됩니다.
>
> 모든 케이스들이 다르기 때문에 어떤 코어 모드를 사용할지는 고급 기능 — Mobilint SDK qb Runtime Library

> latency를 줄이기보단 throughput을 늘리는데 유리하다고 이해해주시는 것이 맞습니다. 이 부분은 제가
> 담당자 분께 따로 문의하겠습니다.
