## 1. qbcompiler 1.3.0 문서 요청

`dl.mobilint.com` 에서 **qbcompiler 1.3.0 릴리즈는 확인**했습니다.
다만 **문서는 1.2 까지만 제공되고 있어** 1.3.0 사용법을 확인하기 어려운 상황입니다.

- **1.3.0 문서(또는 릴리즈 노트)를 제공받을 수 있을까요?**
- **1.3.0 이 앞서 말씀하신 dynamic RoPE 지원 버전이 맞는지** 확인 부탁드립니다.
  맞다면 **VLM 컴파일 튜토리얼도 1.3.0 기준으로 갱신**되는지, 그 일정도 함께 알려주시면 좋겠습니다.
  (현재 SDK Tutorial 의 `compilation/vlm/` 은 `master`·`release/v1.3.0` 양쪽 모두
  이미지 사이즈 224×224 가 전제입니다)

## 2. 구체적 시나리오

말씀하신 대로 저희 시나리오를 구체적으로 정리해 드립니다.

### 2-1. 서비스 형태

| 항목 | 내용 |
| --- | --- |
| 용도 | **CCTV 영상 기반 이상상황 분류** |
| 입력 | CCTV 스트림에서 추출한 **정지 이미지 1장** (비디오 아님) |
| 원본 해상도 | **720p (1280×720)** 기준, 일부 1080p |
| 채널 수 | **20채널** (동시 운영) |
| 요청 주기 | 채널당 **1 fps** — 매 초 20개 요청이 사실상 동시에 도착 |
| 출력 | **분류 결과 1 토큰** (생성 없음, `max_new_tokens=1`) |
| 분류 대상 | 이상행동 4종 — falldown / fire / intrusion / smoke |
| 프롬프트 | 모든 요청에 **동일한 영문 프롬프트 1개** (아래 2-2) — **22 토큰** |
| 모델 | Qwen3-VL-**2B**-Instruct (더 큰 모델도 검토 가능) |

### 2-2. 재현용 프롬프트와 토큰 구성 (실측)

벤더 측에서 바로 재현하실 수 있도록 **저희가 쓰는 형태를 단순화한 예시**를 드립니다.
이미지는 아무거나 쓰셔도 됩니다.

```
Is this image a dog? Answer with only 'yes' or 'no'. Do not output anything else.
```

- 출력은 **`max_new_tokens=1`** 로 고정 — **1 토큰을 넘기지 않습니다.**
- `yes` / `no` 단일 토큰만 확인하며, 그 이후 decode 는 수행하지 않습니다.
- **프롬프트는 모든 요청에 동일**합니다(이미지만 채널별로 다름).

`Qwen/Qwen3-VL-2B-Instruct` 공식 프로세서로 측정한 토큰 구성입니다.

| 입력 이미지 | `image_grid_thw` | 패치 | **시각 토큰** | 텍스트 토큰 | **prefill 총 토큰** |
| --- | --- | ---: | ---: | ---: | ---: |
| 224×224 | `[1, 16, 16]` | 256 | **64** | 32 | **96** |
| 336×336 | `[1, 20, 20]` | 400 | **100** | 32 | **132** |
| 720p (1280×720) | `[1, 44, 80]` | 3520 | **880** | 32 | **912** |

(텍스트 32 토큰 = 프롬프트 22 + chat template 부가 토큰)

**이 세 조건에서 배치 처리 시의 TTFT(prefill 시간)** 를 확인하고 싶습니다.

### 2-3. 목표

| 항목 | 값 |
| --- | --- |
| **지연 목표** | 20채널 요청이 **전부 완료되기까지 1000ms 이내** |
| 핵심 지표 | **TTFT** (prefill 이후 첫 토큰까지) — 토큰 1개만 보므로 decode 단계는 무관 |
| 가용 NPU | 현재 **MLA100 2장** (필요 시 증설 검토) |
| 배치 | 20장을 **배치로 묶어 처리**했을 때의 지연을 확인하고자 합니다 |

### 2-4. 해상도 요구 — 균형점을 찾고자 합니다

앞선 메일에서 말씀드린 대로, 현재 static 빌드는 **224×224 / 시각 토큰 64개**로 고정되어
CCTV 원거리 객체나 세부 단서가 사라지는 문제가 있습니다.

다만 **네이티브 720p(시각 토큰 880개)를 고집하는 것은 아닙니다.**
말씀해 주신 성능(8 batch 약 5000 TPS)을 기준으로 역산하면, 저희가 쓸 수 있는
**이미지당 토큰 예산**은 아래와 같이 계산됩니다.

| 가정 | 2장 합산 처리량 | 이미지당 허용 토큰 | 대략 해상도 |
| --- | ---: | ---: | --- |
| 5000 TPS 가 **카드 1장 기준**이라면 | 10,000 TPS | 약 **500 토큰** | 패치 40×50 ≈ 640×800 |
| 5000 TPS 가 **2장 합산 기준**이라면 | 5,000 TPS | 약 **250 토큰** | 패치 ~31×32 ≈ 500×512 |

**여기서 확인 부탁드릴 점이 있습니다 — 말씀해 주신 5300 TPS / 5000 TPS 가
NPU 1장 기준인지, 여러 장 합산 기준인지**를 알려주시면 저희가 목표 해상도를
확정할 수 있습니다. 이 값에 따라 쓸 수 있는 토큰 예산이 2배 차이가 납니다.

정리하면 저희가 원하는 것은 **"네이티브 해상도 전부"가 아니라,
1000ms 안에 들어오는 선에서 가능한 한 높은 해상도**입니다.
그래서 **토큰 수별 TTFT 곡선**(예: 64 / 256 / 512 / 1024 토큰)을 주시면
저희가 정확도와 속도의 균형점을 직접 고를 수 있어 가장 도움이 되겠습니다.

### 2-5. 현재 측정값 (참고)

이전 메일에서 공유드린 값입니다. **224×224 / 시각 토큰 64개 조건**입니다.

| 채널 | MLA100 1장 | MLA100 2장 |
| ---: | ---: | ---: |
| 20 | 3026 ms | **1580 ms** |

- 코어모드 vision/text 모두 `global8`, 배치 미사용, 카드당 스레드 2개
- 카드 확장 효율 1.92×, 채널 수에 선형

말씀해 주신 코어모드 권장(**이미 batch 처리 중인 경우 vision 은 `single` 코어 8개 비동기**)은
저희 조건에 해당하는 것으로 이해했고, **저희 쪽에서도 재측정해 보겠습니다.**
