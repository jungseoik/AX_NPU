# Qwen3-VL 배치32 검증서버 (`validation_server_bs32`) — 구현·실측

Mobilint가 용량 문의(문의 06)에 대응해 제공한 **배치 프리필 빌드**를 기존 검증서버 형태
그대로 쓸 수 있게 만든 기록. 대상: `third_party/Product-AI-mono/.../npu_pe_2stage/validation_server_bs32`.

- 비교 대상(비포): `validation_server`(batch1) — `reports/performance/qwen3vl/NPU_qwen3vl_vendor_vs_legacy.md`
- 측정 환경: 이 서버 / NPU `/dev/aries1~3` / 컨테이너 cpuset **8코어** / 224×224 / 1토큰 출력
- 벤더 패키지를 수정하지 않고 볼륨 마운트로만 썼다(무결성 검사 769/769 유지).

## 2. 수집 창 — 적응형이 필요한 이유

배치는 "모아야" 성립하는데, 모으려고 기다리면 한가할 때 단건이 손해를 본다. 1카드 실측:

| 창 | 단건 | 20건 | 판정 |
|---|---:|---:|---|
| 0 ms | 162.9 ms | 3337.5 ms | 배치가 아예 안 된다(장당 167ms = batch1 과 동일) |
| 5 ms | 193.4 ms | 1365.7 ms | |
| 20 ms | 195.5 ms | 1314.3 ms | |
| 50 ms | 228.7 ms | 1320.4 ms | 단건이 40% 손해 |
| **probe 2 ms + 창 10 ms** | **176.5 ms** | **1354.7 ms** | 채택 |

**채택안**: 첫 건을 잡은 뒤 **2 ms probe** 로 후속 유무만 본다.
없으면 즉시 단건 처리(b1 디코더), 있으면 10 ms 까지 모아 b32 로 돈다.
동시 도착은 마이크로초 간격이라 2 ms probe 로 충분히 잡힌다.

## 3. 벤더 구현이 강제하는 제약 3가지

### 3.1 `burst()` 동시 호출 금지
디코더 KV 캐시를 공유해 `_burst_lock` 이 `RuntimeError` 로 막는다.
→ **카드당 워커 스레드 1개**로 직렬화한다.

### 3.2 한 묶음의 토큰 길이가 모두 같아야 한다
`text_batch` 가 명시적으로 검사한다:
```python
lengths = [r.embeds.shape[1] for r in requests]
if len(set(lengths)) != 1:
    raise ValueError("Group requests by processed resolution/token count before batching")
```
프롬프트가 다르면 토큰 수가 달라지므로 **한 burst 에 섞을 수 없다.**
검증서버는 카테고리별 프롬프트가 7종이라 **프롬프트별로 묶어** 각각 burst 한다.

| 1카드 20건 | median |
|---|---:|
| 1종 단일 | 1338.5 ms |
| 4종 섞임 | 1431.5 ms (+7%) |

섞이면 묶음이 쪼개져 느려진다. **카테고리 종류가 늘수록 배치 이득이 줄어든다** —
프롬프트 길이를 맞춰 패딩하면 한 묶음으로 갈 수 있으나 정확도 영향이 미검증이라 미채택.

### 3.3 프롬프트는 실은 건별로 바꿀 수 있다
`Classifier(prompt=...)` 로 생성 시 고정처럼 보이지만, 실제로는 `prepare()` 가 매 건
`self.prompt` 를 읽어 토크나이즈한다(runtime.py:132). 워커가 묶음마다 갈아끼우면
인스턴스 하나로 카테고리별 프롬프트를 전부 처리할 수 있다.

검증 — 프롬프트가 실제로 동작을 바꾸는지(같은 이미지, 다른 질문):

| | dog 이미지 | cats 이미지 |
|---|---|---|
| "is this a dog?" | yes ✓ | no ✓ |
| "is this a cat?" | no ✓ | yes ✓ |
| "contains an animal?" | yes ✓ | yes ✓ |
| "is there fire?" | no ✓ | no ✓ |

**8/8 정답.**

## 4. 카드 선택 — `qsize()` 로 고르면 안 된다

처음엔 큐가 가장 짧은 카드를 골랐다. 그런데 **워커가 큐를 즉시 비우므로**,
동시에 들어온 요청이 전부 `qsize()==0` 을 보고 같은 카드에 몰렸다:

| | 수정 전 | 수정 후 |
|---|---:|---:|
| 3카드 20스레드 동시 `ask()` | 1325.8 ms ❌ (1카드와 동일) | **632.6 ms** |
| 2카드 | 1093.5 ms | **739.6 ms** |
| 1카드 | 1478.3 ms | 1258.7 ms |

`ask_batch` 는 한 스레드가 **순차** 제출이라 제출 직후 `qsize` 가 1이 되어 자연히 다음
카드로 넘어갔다 — 그래서 그쪽만 정상으로 보였고 버그가 가려졌다.

**수정**: 제출 시 올리고 완료 콜백에서 내리는 `inflight` 카운터로 고르고,
동률이면 라운드로빈 인덱스로 시작점을 돌려 흩는다.

> 교훈: 배치 API 와 동시요청 경로를 **따로** 재야 이런 게 드러난다.

## 5. 패키징

| | batch1 | bs32 |
|---|---|---|
| Python | 3.12 (ubuntu:24.04) | **3.10 (ubuntu:22.04)** — 휠이 cp310 |
| qbruntime | 1.2.0 (tar + so 전개) | **1.4.0+repack1** (휠에 so 포함) |
| mblt-model-zoo | 1.3.1 | **2.3.0+tta1** |
| 실행 코드 | model-zoo 내장 | 벤더 `pia_vlm/` (`/opt/pia_vlm`) |
| 모델 | HF 자동 다운로드 | **볼륨 마운트 3.4GB** |
| 디바이스 | 쓸 카드만 매핑 | **전 노드 + `/sys:ro`**, 쓸 카드는 env 선택 |
| 세마포어 | 8 | **96** |

**디바이스 매핑이 바뀌는 이유**: qbruntime 1.4.0 은 `/sys/class/aries` 로 장치를 열거한 뒤
`/dev/ariesN` 을 연다. 일부 노드만 넘기면 열거 단계에서 `Acc_DeviceNotFound` 로 죽는다.
전 노드를 넘기고 실제 여는 카드는 `NPU_PE_2STAGE_VLM_DEVICE_IDS` 로 고른다.
(k8s 는 device plugin 이 할당분만 노출하므로 `auto` 로 두면 된다.)

**세마포어를 8 로 두면 안 되는 이유**: 카드당 워커 1개가 최대 32건을 묶는데
세마포어가 8이면 9번째부터 서버 앞단에서 막혀 큐에 도달하지 못한다 → 배치가 성립하지 않는다.

## 6. HTTP 경유 e2e

서버를 실제로 띄우고 HTTP 로 두드린 결과(2카드, 720p 썸네일 base64):

| 항목 | 결과 |
|---|---|
| `/health` | ok (NPU 로드 11초) |
| `/v1/chat/completions` 라벨 정확도 | **4/4** (dog?/cat? × dog/cats 교차) |
| `/api/v1/validate` 계약 | `status='discarded' reason='vlm_rejected'` 정상 |
| 20건 동시 판정 | **20/20** |

**썸네일은 bytes 로 그대로 넘긴다.** batch1 판은 base64 → PIL 로 풀어 넘겼는데,
bs32 풀은 벤더 `Classifier` 가 bytes 를 받으므로 PIL 을 다시 JPEG 로 인코딩해야 한다.
720p 기준 이 왕복이 통째로 낭비다 — 단건 327.3 → **245.0 ms**.

### ★ 격차의 정체 — HTTP 가 아니라 **프롬프트 길이**였다

20채널이 풀 직접 호출 739.6 ms 인데 HTTP 경유는 median 1868.0 ms 로 2.5배였다.
클라이언트를 컨테이너 밖 다른 코어(`taskset 24-31`)로 빼도 그대로였다 — 클라이언트 경쟁이 아니다.

같은 프로세스에서 계층을 분해하니 답이 나왔다(2카드, **운영 `fire_ret` 프롬프트**):

| 계층 | 20채널 median |
|---|---:|
| A. `pool.ask` 직접 | 1261.0 ms |
| B. + b64 디코드 · 세마포어 · executor(asyncio) | 1304.3 ms (**+43 ms**) |

**플럼빙 비용은 43 ms 뿐이다.** A 가 이미 1261 ms 인 게 핵심 —
앞선 739.6 ms 는 **짧은 테스트 프롬프트**(81자)로 잰 값이고, 운영 프롬프트는 훨씬 길다:

프리필 비용은 시퀀스 길이에 붙으므로 프롬프트가 길수록 직접 느려진다. 2카드 실측:

| 프롬프트 | 문자 | 토큰 | 단건 | 20채널 | 장당 |
|---|---:|---:|---:|---:|---:|
| (테스트용 짧은 것) | 75 | 31 | 172.4 ms | **939.9 ms** | 47.0 ms |
| `smoking_ret` | 128 | 39 | 179.1 ms | **911.5 ms** | 45.6 ms |
| `elvfalldown_ret` | 428 | 106 | 237.3 ms | 1325.5 ms | 66.3 ms |
| `climbingup_ret` | 534 | 126 | 234.5 ms | 1255.1 ms | 62.8 ms |
| `fire_ret` | 745 | 182 | 242.6 ms | 1746.9 ms | 87.3 ms |
| `falldown_ret` | 832 | 193 | 248.5 ms | 1525.3 ms | 76.3 ms |

- **31~39토큰이면 2장으로 20채널 900~940 ms — 목표 1000 ms 통과.**
- **182토큰(`fire_ret`)이면 1746.9 ms — 통과 못 한다.** 토큰이 ~6배면 지연이 ~1.9배다.
- 단건은 172.4 → 248.6 ms 로 완만하다(+44%). **배치일수록 프롬프트 길이가 비싸다** —
  묶음 전체의 프리필 토큰이 같이 늘기 때문.

## 7. ★ 운영 프롬프트로 카드 수 스윕 — 실제 답

가장 긴 두 프롬프트로 1/2/3카드를 다시 쟀다(20채널 동시, 전부 **정답 20/20**):

| 카드 | `fire_ret` (182토큰) | `falldown_ret` (193토큰) |
|---:|---:|---:|
| 1 | 2155.0 ms | 1827.1 ms |
| 2 | 1266.9 ms | 1362.3 ms |
| 3 | **1050.9 ms** | **934.2 ms** ✅ |

**결론: 운영 프롬프트를 그대로 두면 3장이어야 1000 ms 근처다.**
`falldown_ret` 은 3장에서 934.2 ms 로 통과하고, `fire_ret` 은 1050.9 ms 로 아슬하게 미달이다.

선택지는 둘이다.

1. **카드 3장**을 쓴다 — `fire_ret` 은 여전히 5% 초과다.
2. **프롬프트를 줄인다** — 39토큰(`smoking_ret`)이면 2장으로 911.5 ms 다.
   `fire_ret`(745자)·`falldown_ret`(832자)는 예시 나열이 길어 줄일 여지가 크다.
   **정확도를 유지하며 줄일 수 있는지는 별도 검토가 필요하다**(탐지 품질 문제, 이 리포트 범위 밖).

> 측정 편차 주의: 같은 2카드 `fire_ret` 이 독립 실행에서 1746.9 ms 와 1266.9 ms 로 나왔다(~30%).
> 카드 점유·CPU 경합에 민감하므로 경계선(1000 ms 근처) 판단은 여러 번 재고 판단할 것.

## 8. HF 배포 — 용량 한도와 해결

업로드 중 `Private repository storage limit reached` 로 막혔다. 원인과 해결 기록.

### 원인 — `usedStorage` 는 **과거 리비전까지 과금**한다

| | |
| --- | --- |
| 계정 `PIA-SPACE` | Pro |
| org `PIA-SPACE-LAB` | **무료 플랜**, private 83.85 GiB 사용 중 (한도 도달) |

`MXQ_NPU` 는 org 소유라 org 쿼터를 쓴다. 그런데 현재 파일 합계는 10.71 GiB 인데
`usedStorage` 는 15.73 GiB 였다 — **차이 5.01 GiB 가 죽은 리비전**이다(189 커밋).
앞서 지운 1.1.2 열화 산출물이 히스토리에 남아 계속 과금되고 있었다.

조회 방법:
```
GET https://huggingface.co/api/models/<repo>?expand[]=usedStorage
```

### 해결 — 히스토리 스쿼시

```python
api.super_squash_history(repo_id="PIA-SPACE-LAB/MXQ_NPU", branch="main", commit_message="...")
```

| | 전 | 후 |
|---|---:|---:|
| 커밋 | 189 | **1** |
| 파일 | 135 | 135 (전부 보존) |
| 현재 파일 | 10.714 GiB | 10.714 GiB (동일) |

★ **`usedStorage` 수치는 즉시 안 줄어든다**(GC 비동기). 스쿼시 직후에도 15.727 GiB 그대로였다.
그러나 **쿼터는 바로 풀려서** 막혔던 업로드가 성공했다 — 수치만 보고 실패로 판단하지 말 것.
사전 확인으로 레포 전체에 특정 sha 고정 참조가 없음을 확인했다(40곳 전부 `main`).

### 결과

스쿼시 직후 막혔던 3개 파일이 전부 올라갔다(`vision.mxq` 30.4s, `model.safetensors` 5.9s,
`decoder-b1.mxq` 13.6s). `qwen3vl/bs32/` **27개 / 3.348 GiB 완료**.

> `model.safetensors` 1196 MB 가 5.9초에 끝난 건 HF 의 content-addressed 저장소(XET)가
> 같은 블록을 이미 갖고 있어서다(공개 Qwen3-VL 가중치와 동일).

### 참고 — 회수 여지가 남은 곳

| 레포 | usedStorage | 현재 파일 | 군살 |
|---|---:|---:|---:|
| PE-Core-L14-336 | 22.01 GiB | 13.80 | **8.21** |
| FT_PE-Core-L14-336_250804 | 10.27 GiB | 6.70 | **3.57** |
| SSAVE | 6.10 GiB | 4.01 | **2.09** |

동일 sha256 중복도 `MXQ_NPU` 안에 1.47 GiB 있다(최상위 `single/multi/global4/global8` =
`W8A16/<scheme>` 사본, SDK 버전폴더 중복). 단 최상위 4개는 **레거시 폴백 경로**라 지우면
구버전 코드가 깨진다.

## 9. 이미지 빌드에서 걸린 것 2가지

### 9.1 `--no-deps` 없이 설치하면 런타임이 덮어써진다

`mblt_model_zoo` 의 메타데이터는 `mobilint-qb-runtime>=1.2.0` 을 요구하는데,
우리가 넣는 휠의 **배포명은 `qbruntime`** 이라 이름이 안 맞는다.
그냥 설치하면 pip 가 PyPI 에서 구버전 런타임을 끌어와 덮어쓰고,
`mblt-tracker`·`cityscapesScripts`·`matplotlib` 같은 무거운 의존도 따라온다.

→ **두 휠 모두 `--no-deps` 로 설치**하고, 실제 의존은 `requirements.txt` 가 고정한다.
   (벤더 재현 이미지 `setup/vlm_repro/Dockerfile.runtime` 도 같은 방식이었다.)

### 9.2 "추론에 안 쓸 것 같은" 의존을 빼면 기동 중 죽는다

`faster-coco-eval`·`gdown`·`matplotlib`·`requests`·`tqdm` 을 뺐더니
컨테이너가 모델 로드 전에 죽었다:

```
mblt_model_zoo/vision/utils/datasets/dataloader.py:13
    from faster_coco_eval import COCO
ModuleNotFoundError: No module named 'faster_coco_eval'
```

`import mblt_model_zoo` 가 **vision 서브패키지를 통째로 eager import** 한다.
VLM 경로만 쓰더라도 detection 쪽 의존이 전부 필요하다.

→ **벤더 `requirements-runtime.txt` 목록을 그대로 따를 것.** 판단해서 빼지 말 것.

## 10. 미해결

- **프롬프트 혼재 시 배치 효율**: 카테고리가 많이 섞이는 실제 트래픽에서 얼마나 손해인지 미측정.
- **프롬프트 단축**: `fire_ret`·`falldown_ret` 을 줄이면 목표를 통과할 수 있으나, 정확도 영향 미검증.
  (탐지 품질 문제라 이 리포트 범위 밖 — 별도 평가 필요)
- **측정 편차**: 같은 조건(2카드 `fire_ret`)이 독립 실행에서 1746.9 / 1266.9 ms 로 ~30% 흔들렸다.
  경계선 판단은 반복 측정이 필요하다.
