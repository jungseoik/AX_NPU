## 1. 결론

1. **튜닝(OPTQ+SWS)이 3개 양자화 모두에서 정확도를 올린다.** 1.1.2에서 전부 떨어뜨렸던 것과 정반대다.
2. **코어모드는 정확도에 영향이 없다.** 같은 양자화·튜닝이면 4모드 cos가 소수 4자리까지 동일하다.
   코어모드는 지연 특성만 바꾼다.
3. **W8A16 + 튜닝(0.9946)이 현행 배포본(0.9937)보다 정확하다.** 크기·속도는 동일 → 사실상 공짜 교체.
4. **W4A8 + A16×5 + 튜닝이 0.9420**으로, 크기 −42%면서 가장 빠르다(20ch 19.94 img/s).
   튜닝 없는 W4A16(0.9175)보다 정확하면서 더 빠르다.

**코어모드 관찰 (재측정 기준)**

- **`global8` 이 단건 최소**다: 61~73ms. 다른 모드의 1/2~1/4 수준이며, 레포에 기록돼 있던
  "단건 저지연 global8 ≈71ms" 와 일치한다.
- **배치는 양자화에 따라 갈린다.**
  - W8A16 → `global4` 가 8ch·20ch 모두 우세(20ch 1272.6 vs single 1375.7)
  - W4A16 / W4A8 → `single` 이 우세(20ch 1005.0 vs global4 1166.9)
- `multi` 는 전 구간 최악이다(20ch 5.6~7.4s). **쓰지 말 것.**
- `global8` 은 단건 최강이지만 배치에서는 밀린다(20ch에서 global4·single보다 느림).

## 5. ★ 이전 W4A8 수치(0.8932)는 잘못된 값이었다

[`NPU_pe_quant_tuning_compiler_version.md`](NPU_pe_quant_tuning_compiler_version.md) 에 기록한
W4A8_L5A16 1.2.0 값 **0.8932 는 A16 텐서 5개가 빠진 산출물**이었다. 정정값은 **0.9420**.

- 원인: 그 측정에 쓴 임시 하네스를 `--preset w4a8_l5a16 --optq --sws` 로 호출했는데, 그 하네스는
  A16 텐서를 `--act16` 으로만 받는 구조였다. `--act16` 을 넘기지 않아 **qk16 25개만 16bit**였다.
  컴파일 로그에도 `[qk16] score MatMul 25개` 만 있고 A16 라인이 없다.
- 이번 GPU 매트릭스는 `compile_quant_tuning_matrix.py` 가 `A16_TENSORS_W4A8` 5개를 정확한 mblt
  이름으로 주입한다 → 0.9420.
- **W4A8 계열은 A16 주입 여부를 로그로 반드시 확인할 것.** `[quant] activation16=30`(qk16 25 + A16 5)
  이어야 하며, 25면 A16이 빠진 것이다. 과거 cos 0.2609 오측정도 같은 계열의 문제였다.

정정 후 W4A8 계열의 버전 비교는 아래와 같다(둘 다 A16 정상 주입).

| W4A8 + A16×5 | 튜닝 없음 | +OPTQ+SWS | 튜닝 효과 |
| --- | ---: | ---: | ---: |
| qbcompiler 1.1.2 | 0.8790 | 0.8560 | −0.023 |
| qbcompiler **1.2.0** | 0.8884 | **0.9420** | **+0.054** |

벤더 회신값(0.905)과 비교하면 **1.2.0 실측이 오히려 이를 넘어선다**(0.9420).

## 6. 부수 확인

- **베이스라인의 컴파일러 버전 무관성**이 3개 양자화 전부에서 확인됐다(이전엔 W4A16만).
  W8A16 none: 1.1.2 0.9937 ↔ 1.2.0 0.9937. W4A16 none: 0.9110 ↔ 0.9175. W4A8 none: 0.8790 ↔ 0.8884.
- **컴파일 환경(CPU/GPU) 무관**: W8A16 sws_optq CPU 0.9951 ↔ GPU 0.9946, W4A16 sws_optq CPU 0.9642 ↔ GPU 0.9654.
- **이미지 세트 민감도**: 다른 20장으로 재측정해도 W8A16은 소수 4자리까지 동일, 4bit 계열은 ±0.005 내에서 움직인다.
  회귀 판정 허용오차 ±0.005는 4bit 계열에서 빠듯하므로, 이 리포트의 24점을 표준 세트 기준으로 재앵커링했다
  (`verify_quant_tuning_matrix.py` 의 `BASELINE_120`).

## 7. 배치 출력 무결성 — 72/72 비트 동일 (2026-09-04)

**"배치로 넣으면 출력이 깨지지 않나"에 대한 확인.** 같은 mxq로 **1장씩 N번** 돌린 결과와
**N장 배치 한 번**의 결과를 장별로 대조했다.

| 축 | 값 |
| --- | --- |
| 양자화 | W8A16 / W4A16 / W4A8_L5A16 (전부 `sws_optq`) |
| 코어모드 | single / multi / global4 / global8 |
| 배치 | 1 / 4 / 8 / 12 / 16 / 20 |
| 케이스 | 3 × 4 × 6 = **72** |

**결과: 72/72 전부 `np.array_equal` 참** — cos 1.0 수준이 아니라 **부동소수 오차조차 없다.**
`multi` 모드도 동일하다(느릴 뿐 출력은 정확하다).

```
[ok ] single   B=20  최저 cos=1.00000000  비트동일 20/20
[ok ] multi    B=20  최저 cos=1.00000000  비트동일 20/20
[ok ] global4  B=20  최저 cos=1.00000000  비트동일 20/20
[ok ] global8  B=20  최저 cos=1.00000000  비트동일 20/20
```

**왜 안전한가**: `MXQInferenceFull.infer(batch)` 는 이미지를 카드에 라운드로빈으로 나눠
**동기 `infer()`** 를 스레드풀로 돌리고 결과를 `out[i]` 에 인덱스로 되꽂는다.
레포가 금지하는 **`infer_async` 다건 동시 제출**(→ 출력 깨짐) 패턴이 아니다.

§2 의 cos 자체도 20장을 한 번에 배치로 넣고 장별로 잰 값이며, 24종 모두 `cos_min` 이
정상 범위였다(최저 0.8952, 깨짐 시 나타나는 0 근처 값 없음).

재현: `python reports/scripts/verify_pe_batch_output.py --device 0`
(불일치 시 어느 이미지가 틀렸는지 출력하고 exit 1)

## 8. ★ 지연 측정 주의 — 이 서버는 공유 카드다

최초 측정(2026-09-04 오전)은 호스트 경합 중이었고, 지연이 실제보다 **최대 29% 높게** 나왔다.
cos 는 영향이 없다(연산 결과는 부하와 무관).

| 조합 | 경합 시 | 저부하 재측정 | 차이 |
| --- | ---: | ---: | ---: |
| W8A16 none global4 20ch | 1674.9 | **1279.5** | −24% |
| W4A16 sws_optq global4 8ch | 658.3 | **474.8** | −28% |
| W4A16 sws_optq single 20ch | 1131.6 | **1005.0** | −11% |
| W8A16 none global8 1ch | 187.2 | **73.4** | −61% |

**그래서 지켜야 할 것**

1. **다른 날 잰 지연끼리 절대 비교하지 말 것.** 버전·빌드 비교는 **같은 세션에서 교차 측정**해야 한다.
2. 같은 실행 안의 상대 비교(모드 간, 양자화 간)는 유효하다.
3. 측정 전 `uptime` 과 `mobilint-cli status` 로 부하를 확인할 것. 이 서버는 운영 k8s 추론 파드가
   카드를 함께 쓴다(측정 당시 load average 5분 평균 16.94).

**철회**: 최초 리포트에서 W4A8 global8 의 1ch `62.4ms` 를 "워밍업 잡음"으로 표시했으나
**잘못이었다.** 재측정에서 61.0 / 61.3ms 로 재현됐다. 그때 경합이 잠깐 풀린 정상값이었고,
오히려 같은 표의 175~190ms 쪽이 경합값이었다.
