# PE 비전 인코더 양자화 스킴 비교 — W8A16 / W4A16 / W4A8+A16

**결론 요약**
- 기존 배포본은 순수 INT8이 아니라 **W8A16**이다(컴파일러 Activation 기본값이 output·ffn 16bit).
- **W4A16은 동작한다** — 크기 −42%, 20채널 처리량 +13%, 단건 지연 −12%. 대가는 cos 0.9936 → 0.9135.
- **W4A8 + A16 5개는 실패** — cos 0.2609로 붕괴. 배포하지 않는다.
- 과거 "4bit 불가(no-op)" 판정은 **`mixed_precision` 필드 한정**이었고, 역할별 비트폭 지정
  (`BitConfig.Transformer.Weight(...=4)`)은 정상 동작한다. → [`NPU_batch_latency.md`](NPU_batch_latency.md) §6 정정

측정: 2026-09-02 / NPU 1장(`/dev/aries7`) / calib COCO val2017 200장 / 정확도 = 원본 PyTorch 임베딩 대비
코사인 유사도(COCO 20장 평균) / 지연 = 채널 N개를 한 배치로 넣어 전부 끝나는 시간, 3회 중앙값
(동기 `infer` + 스레드풀 = 출력이 유효한 표준 패턴).

## 2. 읽는 법

### 정확도 vs 속도

| 스킴 | cos | 크기 | 12채널 지연(global4) | 판정 |
| --- | ---: | ---: | ---: | --- |
| W8A16 | **0.9936** | 327 MB | 756 ms | **기본값** — 정확도 필요한 모든 경로 |
| W4A16 | 0.9135 | 189 MB (−42%) | **666 ms (−12%)** | 속도·메모리 우선 경로에서 선택 가능 |
| W4A8+A16 5개 | **0.2609** | 188 MB | 590 ms | **사용 불가** |

- 12채널 500ms 기준(과제 목표)은 **어떤 스킴으로도 1장에서 충족되지 않는다**. W4A16으로도 666ms다.
  카드 증설이 여전히 정답이다(6채널씩 2장 분산).
- 양자화를 낮춰 얻는 이득은 **채널이 많을수록 커진다** — 1채널은 −12%, 20채널은 −12~26%.

### 코어모드 특성은 양자화와 무관하게 유지된다
- **global8**: 단건 최저지연(59~73ms). 단일 스트림 응답성 우선.
- **global4**: 다채널 최고 처리량. 8채널 이상이면 항상 유리.
- **multi**: 다채널에서 4~5배 느리다. **쓰지 말 것.**

### W4A8은 왜 실패했나
activation을 8bit로 내리면 outlier가 큰 텐서에서 스케일이 무너진다. 우리 모델 프로파일링
(`pe_npu/profile_activations.py`, 기준 `ratio = max/p99.9`)에서 상위 5개를 16bit로 유지했는데도
cos 0.26이었다. 상위 6~15위도 6.6~11.1× 로 계속 이어져 **5개로는 부족**하다는 뜻이다.

| 순위 | 텐서 | ratio |
| --- | --- | ---: |
| 1 | L3.mlp.c_proj | **74.9×** |
| 2 | L12.mlp.c_proj | 16.2× |
| 3 | L10.mlp.c_proj | 14.4× |
| 4 | L12.mlp.gelu | 13.0× |
| 5 | L10.mlp.gelu | 12.3× |
| 6~15 | L7/L2/L11/L4/L17 등 | 6.6~11.1× |

> **미해결**: 같은 비트 설정인데 **global8만 cos 0.8709**로 다른 3모드(0.2609)와 크게 다르다.
> 코어모드에 따라 레이어 분할·융합이 달라지며 붕괴 지점이 바뀐 것으로 보이나 확정하지 못했다.

## 3. 정확도 보정 옵션 — OPTQ / SearchWeightScale

W8A16은 보정 없이도 cos 0.99가 나와 두 옵션을 쓴 적이 없었다(둘 다 qbcompiler 1.1.2에 **존재**했으나
기본 꺼짐). W4로 내려가면서 필요해졌다.

| 옵션 | 하는 일 | 우리 실측 |
| --- | --- | --- |
| **SearchWeightScale** | 스케일 후보를 탐색해 clipping·rounding 오차 합이 최소인 값 선택 | W4A16 단독 적용 시 **cos 0.9135 → 0.8786 (악화)**, 컴파일 78분 → 118분 |
| **OPTQ** (GPTQ 계열) | 열 단위로 양자화하며 발생한 오차를 남은 가중치로 보상(헤시안 근사 사용) | 검증 진행 중 |

벤더 예제는 두 옵션을 **함께** 켠다. SWS 단독이 역효과였던 것은 OPTQ와 병용해야 의미가 있기 때문일
가능성이 있어 문의 05로 확인 중이다 →
[`../inquiries/05_a16_selection_followup/EMAIL.md`](../inquiries/05_a16_selection_followup/EMAIL.md)

## 4. 컴파일 비용 (이 서버: GPU 없음, 96코어)

| 조건 | 소요 |
| --- | ---: |
| W8A16 / W4A16, calib 200장, 단독 실행 | 72~78분 |
| 〃 4개 병렬(스레드 제한 없이) | **개당 5~6시간** |
| W4A16 + SWS | 118분 |
| W4A16 + OPTQ + SWS | calibration 단계만 1.5시간+ (진행 중) |

**병렬 실행 시 스레드를 반드시 나눌 것.** 제한 없이 4개를 띄우면 프로세스당 176스레드 × 4 = 704개가
96코어를 두고 경합해(초당 컨텍스트 스위치 6만 회, idle 15~21%) 병렬 이득이 사라진다.
`--threads $(nproc / 동시실행수)` 로 나눠 준다.

**GPU 서버면 크게 빨라진다.** `--device gpu` 는 calibration 연산을 GPU로 보낸다. 기존 측정
([`compile_benchmark.md`](compile_benchmark.md))의 "GPU 이득 6%"는 **random calib 1샘플** 조건이라
calibration이 짧았던 경우다. calib 200장 + OPTQ에서는 무거운 연산(대형 행렬곱, 헤시안 누적·분해)이
전부 GPU 대상이라 수 배 단축이 기대된다. 실행: `bash setup/compile_in_docker.sh --gpu ...`

## 5. 재현

```bash
# 컴파일 (도커 — CPU/GPU 서버 공통, 이미지·디바이스 자동 선택)
bash setup/compile_in_docker.sh --calib-data-path download/calib_coco_hwc \
     --save out/pe_w4a16_single.mxq --quant w4a16 --qk16 --scheme single

# 12조합 벤치 (cos + 1~20채널)
python reports/scripts/bench_quant_schemes.py --device 7
```
